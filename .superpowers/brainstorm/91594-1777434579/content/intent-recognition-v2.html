四、全量 Skill 摘要机制

设计说明
  • 所有 Skill 统一用结构化摘要注入 System Prompt
  • 每个 Skill 摘要 3~5 行，包含：name, page, type(read/write), trigger 描述, 核心参数列表
  • 20~30 个 Skill 总计约 100~150 行，主流 LLM 上下文窗口完全可承载
  • LLM 根据摘要直接选择 Skill 并输出 Tool Call
  • 完整 Tool 参数 Schema 在 Tool Dispatcher 侧维护，做参数校验和补全
  • 跨页面意图和本页面意图处理路径完全一致
Skill 摘要示例
Skill: record_bill Page: 记一笔 Type: write Trigger: 用户提到金额、商家、消费场景等记账相关信息 Params: amount(必填), category, merchant, date(默认今天), note --- Skill: bill_statistics Page: 账单详情/报表 Type: read Trigger: 用户询问消费统计、同比环比、分类占比等 Params: time_range, category, compare_type(同比/环比) --- Skill: budget_adjust Page: 预算 Type: write Trigger: 用户要求修改预算金额或设置新预算 Params: category(必填), amount(必填), period(月/周)

五、可验证置信度机制

LLM 输出特征置信度判定系统行为
输出明确 Tool Call + 参数完整HIGH只读 → 直接执行；写操作 → 展示确认面板
输出 Tool Call + 缺少关键参数（如记账无金额）MEDIUM追问缺失参数："金额是多少？"
未输出 Tool Call，LLM 用自然语言反问LOW（LLM 自行澄清）直接返回 LLM 的澄清问题
输出 Tool Call + 参数值异常（金额=0/负数/未来日期）MEDIUM确认异常值："金额是 0 元，确认吗？"
写操作（无论置信度）—一律展示操作预览 + 确认按钮
置信度由 Tool Dispatcher 根据输出结构客观判断，不依赖 LLM 自评分数。这是与传统方案的核心区别。

六、业务规则兜底层

规则触发条件处理方式
金额异常超过该分类历史最大值 3 倍追问确认："这笔 8000 元的餐饮消费，确认金额正确吗？"

时间异常记账日期超过 30 天前或在未来追问确认日期

七、反幻觉机制

7.1 核心原则

LLM 在本系统中的角色是"推理引擎 + 表达引擎"，不是"数据源"。所有涉及用户财务数据的回答，必须且只能基于 Tool 返回的结构化结果。

7.2 五层防线
第一层：System Prompt 硬约束
  • 注入明确指令："你没有任何账单、预算、资产数据的记忆。所有数据必须通过工具查询获取。如果工具没有返回数据，你必须告知用户'未查询到相关数据'，绝不可以编造或推测任何数值。"
  • 禁止 LLM 使用"大约"、"可能是"等模糊表述来掩盖数据缺失
第二层：Tool 返回结构化数据 + 来源标记
  • 每个 Tool 返回结果包含：data（结构化数据）、source（数据来源：mysql/redis/milvus）、query_time（查询时间戳）、is_empty（是否为空结果）
  • 空结果明确标记 is_empty=true，LLM 据此回复"没有找到相关记录"
第三层：数值一致性校验（关键防线）
  • Tool Dispatcher 在 LLM 生成回复后，提取回复中的所有数值
  • 与 Tool 返回的原始数据做交叉比对
  • 发现不一致时：拦截回复，用 Tool 原始数据替换 LLM 编造的数值，或重新生成
  • 示例：Tool 返回本月餐饮 2180 元，LLM 回复中写了 2200 元 → 拦截修正
第四层：无数据时的明确兜底
  • 查询无结果 → "没有找到 X 的相关记录"
  • 工具调用失败 → "查询暂时出了问题，请稍后再试"
  • 数据不足以支撑分析 → "当前数据不足以进行 X 分析，至少需要 N 个月的记录"
  • 绝不用编造数据来填充回答
第五层：记忆数据的可靠性保障
  • 记忆写入时标记数据来源（用户直接陈述 / 系统推断 / Tool 查询结果）
  • LLM 引用记忆时，系统推断类记忆需要标注"根据历史记录推断"
  • 事实记忆（L2）定期与实际数据校验，过期或矛盾的记忆自动标记为待验证
7.3 反幻觉校验流程图
LLM 生成回复
↓
提取回复中所有数值（金额、百分比、数量、日期）
↓
与 Tool 返回原始数据比对
↓
通过 全部一致 → 放行，流式返回
容差 存在偏差但在容差范围内（如四舍五入差异）→ 放行
拦截 存在明显不一致 → 拦截，用原始数据修正后返回

十一、轻量级 ReAct 多步推理

核心原则

不是所有请求都进 ReAct。由 LLM 第一轮输出的结构特征决定执行路径，不需要额外分类器。

路径判定标准

LLM 第一轮输出判定路径
单个 Tool Call + 参数完整单步直达执行 → 结果给 LLM → 生成回复 → 返回
多个 Tool Call（并行无依赖）单步并行并行执行 → 结果合并给 LLM → 生成回复
多个 Tool Call（有依赖链）进入 ReAct按依赖顺序逐步执行
单个 Tool Call + 后续意图表达进入 ReAct执行 → 观察 → 继续循环
无 Tool Call（纯文本/澄清）直接返回不进入执行流程

ReAct 约束

  • 最大步数：5 轮
  • 写操作打断：遇到写操作暂停循环，展示确认
  • Go 原生实现，不引入外部 Agent 框架

性能预期

路径LLM 调用次数预期延迟
单步直达2 次3~5s
单步并行2 次（Tool 并行）4~7s
ReAct 2 步3 次7~10s
ReAct 3 步4 次10~12s

十二、执行反馈策略

核心思路

预估时间 + 骨架屏为主，步骤通知为辅。体验保障不依赖不稳定的服务端中间推送。

执行计划摘要

进入多步执行时，Tool Dispatcher 返回
{ "type": "execution_plan", "steps": 3, "estimated_seconds": 8, "description": "需要查询资产、负债和预算数据后综合分析" }

前端处理

  • 收到 execution_plan 后展示带进度预估的骨架屏
  • 进度条按预估时间匀速推进（不依赖服务端推送）
  • 每步完成后可选推送 step_done（有则更好，没有不影响）
  • 最终回复走正常流式输出

可靠性对比

方案依赖服务端推送降级模式可用弱网可靠实现复杂度
纯流式反馈强依赖不可用不可靠高
预估 + 骨架屏不依赖完全可用完全可靠低
预估 + 步骤通知（采用）弱依赖降级为纯预估降级为纯预估中
