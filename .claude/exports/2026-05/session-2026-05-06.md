## 一、RAG 预填金额匹配错误

### 1.1 问题
用户说"麦当劳"，RAG 返回 ¥38.00（星巴克的价格），而非麦当劳的 ¥17.80。

### 1.2 根因
- `FillParams` 商户匹配要求 `EffectScore >= 1.0`，麦当劳只有 0.5 不满足
- 跳到分类匹配，命中了同为"餐饮"分类的星巴克（effect_score=1.1）

### 1.3 修复
- 去掉 EffectScore 阈值限制，只要有商户匹配就用
- 用户消息中有金额就直接覆盖 PendingAction 预填值（`mergePendingParams` 不再要求 amt<=0）

## 二、AvgAmount → LastAmount

### 2.1 问题
消费习惯记录取平均值不合理（星巴克 ¥28 美式 + ¥58 套餐，平均 ¥43 哪个都不是）。

### 2.2 修复
- `ConsumptionPattern.AvgAmount` 改为 `LastAmount`（最近一次金额）
- 数据库 migration：`ALTER TABLE consumption_patterns ADD COLUMN last_amount, DROP COLUMN avg_amount`
- 提取逻辑改为按日期排序取最后一笔
- 提示文案从"平均 ¥38.00"改为"上次 ¥38.00"

## 五、单价×数量计算

### 5.1 问题
用户说"咖啡9.9一杯 买了4杯"，只记了 ¥9.90，没有计算 9.9×4=39.6。

### 5.2 方案（方案 C）
1. Engine 正则计算（`calcTotalFromQuantity`）— 覆盖常见模式，100% 准确
2. LM 计算 + Engine 数学校验（`amountFoundInContext` 乘积/求和匹配）— 兜底长尾
3. 量词统一为常量 `unitChars`，支持杯/个/份/瓶/包/袋/盒/箱/碗/碟/盘/张/套/件/双/只/条/块/斤/两/升/辆/艘/匹

### 5.3 多商品求和
- "一个8.8一个10.6" → `calcTotalFromSum` 识别并求和
- `amountFoundInContext` 新增求和校验层

## 六、多笔不同商品消费

### 6.1 问题
用户说"一杯咖啡9.9，一份便当21"，应该记两笔，但只记了第一笔。

### 6.2 方案演进
1. ❌ Engine 正则识别多笔 → 太脆弱，表达模式无穷
2. ✅ LM 识别 + Engine 确认执行：
   - 新增 `create_bills_batch` Tool
   - LM 识别多笔消费，传 items 数组
   - Tool 返回 need_confirm（含明细 + 日期异常提示）
   - 用户确认 → `executeBatchPendingAction` 逐笔调 create_bill

### 6.3 关键设计
- `PendingAction` 新增 `BatchParams []map[string]any`
- `hasBatch` 优先级：LM 同时调 create_bill 和 create_bills_batch 时，跳过 create_bill
- 日期异常合并到批量确认消息中，不单独确认

## 七、双重确认 Bug

### 7.1 问题
多笔消费确认后又弹出确认，需要确认两次甚至三次。

### 7.2 根因链路
1. LM 同时输出 create_bill + create_bills_batch 两个 Tool Call
2. create_bill 的日期异常 Guard 先拦截，存了错误的 PendingAction（无 BatchParams）
3. 用户确认 → 执行单笔 create_bill → LM 继续调 create_bills_batch → 又一次确认

### 7.3 修复
- Engine 层 `hasBatch` 判断：有 create_bills_batch 时跳过 create_bill
- `executeBatchPendingAction` 中 `isConfirmation(ctx)=true`，跳过所有 Guard

### 7.4 致命遗漏
**stream.go 的 `executeWorkflowStream` 一直没更新！** 前端用的是流式端点，engine.go 改了 4 次都没生效。

## 八、isPendingParamAnswer 误拦截

### 8.1 问题
用户说"补充一下吧"被判定为参数回答，走了 RAG 预填而不是 LLM。

### 8.2 修复
从排除式判断改为正向匹配：
- 确认词（"确认"、"好的"等）→ 参数回答
- 纯金额（"30"、"9.9元"）→ 参数回答
- 已知分类名 → 参数回答
- 其他 → 不是参数，走 LLM

## 十二、问题排查规范（教训总结）

### 核心规范
1. **全链路排查** — 改任何逻辑必须排查所有入口（engine.go + stream.go），确认一致性
2. **禁止单点修复** — 不允许只改一处而遗漏另一处相同逻辑
3. **两次不生效就停** — 必须从根因分析完整调用链，不再打补丁

### 反面案例
stream.go 的 PendingAction 存储逻辑从未更新，前端走流式端点导致所有 batch 相关修复都不生效。engine.go 改了 4 次才发现问题不在 engine.go。

## 十三、LLM 幻觉防护反思

### 结论
记账系统接入 LLM，防幻觉是基本安全要求，不需要用户提醒。应该在第一版 create_bill 就包含：
- 金额必须可追溯到用户输入
- LLM 不做任何算术
- 所有写操作必须确认

这属于开发者应具备的领域判断力，不是"优化"而是"必须"。
