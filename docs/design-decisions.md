# 咔皮记账 AI 助手 — 设计决策记录

> 本文档记录头脑风暴阶段达成共识的关键决策，用于指导后续架构设计和实施。

## 一、已确认的核心决策

### 1. LLM 模型策略：模型无关设计
- 抽象 LLM 层，支持多模型切换
- 初期选一个主力模型跑通 prototype，保留扩展性
- LLM 层需统一封装：Prompt 模板、Tool 调用协议、流式输出接口

### 2. 跨页面意图识别：回答 + 跳转建议
- 用户在任意页面提问，助手优先在当前页面上下文内回答
- 回答的同时提供相关页面的跳转入口，用户自行决定是否跳转
- 只读场景：综合数据直接回答
- 写操作场景：先给建议，用户确认后执行

### 3. 记忆系统：六层架构
| 层级 | 名称 | 内容 | 存储特征 |
|------|------|------|----------|
| L1 | 用户画像 | 偏好、习惯、财务特征标签 | 长期，低频更新 |
| L2 | 事实记忆 | 具体财务事实（月租3500、两张信用卡） | 长期，结构化，可被推理引用 |
| L3 | 情景记忆 | 过去的决策上下文和交互场景 | 中长期，关联操作日志 |
| L4 | 对话历史 | 当前及近期对话上下文 | 短期，会话级 |
| L5 | 消费模式 | 从历史账单提取的重复消费模式（商户+分类+加权平均金额） | MySQL + 定时/事件触发提取 |
| L6 | 序列模式 | 消费之间的关联关系（同天相邻账单配对，≥3次有效） | MySQL + 90天硬截断 |

- 严格多租户隔离，用户间记忆信息不可交叉
- 事实记忆需支持结构化财务事实（不只是文本）
- 情景记忆需关联分析结果和操作日志

### 4. Skill 技能系统：混合模式
- **文件层（基础）**：内置 Skill 以 YAML/JSON 定义，随代码部署，文件监听热加载
- **数据库层（覆盖）**：业务自定义 Skill 通过 MySQL 管理，支持 CRUD、版本管理
- 数据库层可覆盖和扩展文件层
- 页面感知：根据请求来源页面动态选择可用 Skill 和工具集

### 5. 写操作策略：软删除 + 操作日志 + 记忆索引
- **所有删除为软删除**，不物理清除（可设 30 天后清理策略）
- **所有写操作记 Operation Log**：who/what/when/before_snapshot/after_snapshot/session_id/trigger（用户原话）
- **记忆关联**：情景记忆自动关联关键写操作的 operation_log ID
- **恢复方式**：用户用自然语言描述 → 记忆检索定位 → 操作日志提供精确快照 → 执行恢复
- 修改操作提供流畅的交互体验，用户可随时通过对话调整任意值
- 回滚本质上退化为"再做一次写入"，降低用户认知负担

## 二、统计分析与预测能力

### 分析能力矩阵

#### 账单分析（已发生事实）
- 同比分析：今年 N 月 vs 去年 N 月（按分类、总额）
- 环比分析：本月 vs 上月（按分类、总额）
- 趋势分析：最近 N 月支出曲线、分类占比变化
- 异常检测：消费显著偏离该分类历史均值时主动提醒

#### 预算分析（计划 vs 现实）
- 预算执行率：已花 / 预算额度，按分类细分
- 预算合理性评估：用户设定预算 vs 过去 3~6 月实际均值，偏差过大时主动提醒
- 预算预警：按当前消费速率预测月底是否超支，提前预警

#### 资产分析
- 净资产变化趋势
- 现金流分析：收入 - 支出的月度/周度趋势
- 负债比率：负债 / 总资产的健康度评估

#### 预测能力
- 消费预测：基于历史数据预测下周/下月各分类预期支出
- 行为预测：预测用户当前时间点最可能的记账行为（早8点→早餐，月初→房租）
- 查询偏好预测：识别用户查询习惯，驱动主动推送
- 未来预算规划：基于历史趋势 + 用户目标，反推各分类建议预算

#### 提醒能力
- 周期性账单提醒（房租、会员、保险到期）
- 预算超支预警
- 异常消费提醒
- 目标进度提醒

### 实现策略：Skill 化分析 + 预计算缓存

**Skill 化**：统计分析封装为内置 Skill，LLM 调用工具获取结构化结果后用自然语言表达
- LLM 不做数值计算，只做推理和表达，保证结果准确可控

**预计算 + 缓存**：
- 高频指标（月度汇总、分类占比、预算执行率）定时预计算，缓存到 Redis
- 低频/个性化分析走实时计算
- 保证 P95 首字延迟 ≤ 5s

### 记忆与预测的协同

- **行为预测 = 统计规律 + 记忆上下文**：统计得出规律，记忆提供个性化修正
- **主动推送 = 时间触发 + 记忆判断**：定时检测 + 记忆中的用户偏好决定是否推送
- **预算建议 = 历史统计 + 用户目标记忆**：不简单取均值，结合用户储蓄目标等记忆做智能建议

## 五、已确认的核心决策（续）

### 6. 连接与会话管理：WebSocket 为主 + HTTP 降级

**主通道：WebSocket 长连接**
- 对话流式输出、服务端主动推送（提醒、预警）均走 WebSocket
- 支持 30~100 路并发长连接

**降级通道：HTTP API**
- 当 WebSocket 不可用时降级为 HTTP POST + SSE 流式响应

**降级策略（关键设计点）：**

触发降级条件：
- WebSocket 连接连续 N 次（如 3 次）握手失败
- 已建立的连接在心跳超时（如 30s 无 pong）后断开，且重连 M 次（如 2 次）失败
- 网络切换事件（WiFi → 蜂窝）导致连接中断

降级行为：
- 切换到 HTTP 模式后，对话请求走 HTTP POST，流式输出走 SSE
- 主动推送改为客户端轮询（间隔可配，如 30s）
- 客户端本地标记当前为降级模式

恢复策略：
- 降级后启动后台探测：每隔 T 秒（指数退避，如 10s → 20s → 40s → 最大 120s）尝试 WebSocket 握手
- 握手成功后不立即切换，先完成一次完整心跳周期确认连接稳定
- 确认稳定后，等当前进行中的 HTTP 请求完成，再切回 WebSocket
- 切换期间保证消息不丢失：通过 message_id 去重 + 服务端消息队列暂存

防抖动机制：
- 短时间内（如 5 分钟）发生 2 次以上 WebSocket→HTTP→WebSocket 切换，锁定 HTTP 模式一段时间（如 10 分钟）
- 避免网络不稳定时频繁切换带来的体验劣化

### 7. 前端 Demo 形态：单页三栏布局
- **左栏：页面上下文模拟器** — 切换当前页面（首页/记一笔/账单/预算/报表/资产），切换后助手的 Skill 集和工具集随之变化，底部展示当前激活的 Skills 列表
- **中栏：对话窗口** — 主交互区，流式输出，支持富文本消息，写操作确认交互
- **右栏：动态内容面板** — 助手返回结构化数据时自动渲染（图表、表格、卡片摘要、操作确认面板）
- 对话区负责自然语言交互，右栏负责数据可视化
- 跨页面回答时，对话区底部附跳转建议链接

### 8. Prototype 页面范围：全页面覆盖
覆盖所有 6 个核心页面，每个页面配备差异化的 Skill 集和工具集：

| 页面 | 核心能力 | 典型交互 |
|------|----------|----------|
| 首页 | 综合概览、主动推送、快速入口 | "今天花了多少"、主动推送月度摘要 |
| 记一笔 | 自然语言记账、批量录入 | "昨天星巴克38元"、"帮我记三笔" |

| 预算 | 预算设置/调整、执行率、合理性评估 | "帮我把娱乐预算调到800" |
| 报表 | 同比环比、趋势分析、分类占比 | "给我看最近三个月的消费趋势" |
| 资产管理 | 资产概览、现金流、综合建议 | "我能不能买这个5000元的相机" |

业务数据通过 Mock 实现，但 AI 交互流程完整真实。

### 9. 整体架构：单体 + 插件化（可拆分的单体）
- 单 Go 服务，内部通过 Go interface 严格解耦各子系统
- 定义清晰的内部 API 边界，当前单进程运行，未来可沿 interface 边界拆为微服务
- 部署形态：单 Docker 容器 + MySQL + Redis + Milvus

**核心子系统及 interface 边界：**

| 子系统 | 职责 | 关键 interface |
|--------|------|----------------|
| Connection Manager | WebSocket/HTTP 双通道、降级恢复 | Connector |
| AI Engine | 会话管理、LLM 抽象层、Tool 调度、流式输出 | LLMProvider, ToolExecutor |
| Skill Manager | 文件加载 + DB 覆盖、页面感知、热更新 | SkillRegistry, SkillLoader |
| Memory Manager | 六层记忆（L1~L6）、多租户隔离、向量检索 | MemoryStore, MemoryRetriever |
| Analytics Engine | 统计分析 Skill、预计算调度、预测 | Analyzer, Predictor |
| Operation Logger | 写操作日志、快照、恢复 | OpLogger, OpRestorer |

### 10. 权限校验：JWT Token + 中间件统一拦截
- 用户登录获取 JWT，Token payload 携带 user_id
- Auth 中间件统一拦截所有 HTTP 请求和 WebSocket 握手
- 各子系统通过 context 获取 user_id，所有数据查询自动带 `WHERE user_id = ?`
- 多租户数据隔离的核心机制：不是角色权限，而是数据归属
- 无需 RBAC/ABAC，未来如需角色体系可在 JWT payload 扩展 role 字段

### 11. 会话连续性：页面切换不中断对话

**核心原则：对话会话（Session）是用户级的，不是页面级的。页面只是上下文参数，不是会话的生命周期边界。**

Session 结构：
```
Session（用户级，持久）
  ├── 对话历史（完整保留，不因页面切换清除）
  ├── 当前 page_context（随页面切换实时更新）
  └── 进行中的任务（ReAct 执行链、待确认的写操作）
```

设计要点：

| 设计点 | 策略 |
|--------|------|
| WebSocket 连接 | 全局持久，挂在 App 层，不随 Vue Router 切换断开 |
| 对话窗口 | 全局组件，不随路由销毁 |
| 进行中的任务 | 继续执行，绑定发起时的 page_context 快照 |
| 新任务 | 使用切换后的新 page_context |
| 写操作确认 | 跨页面可确认，确认面板标注来源页面 |
| 对话历史 | 完整保留，每条消息标记页面来源 |
| HTTP 降级模式 | 同样适用，page_context 通过请求参数传递 |

页面切换时前端行为：
- 发送轻量消息 `{"type": "page_switch", "from": "记一笔", "to": "账单详情"}` 更新服务端 page_context
- 不断开 WebSocket，不清除对话历史
- 进行中的请求继续等待，结果正常展示在对话区

任务与 page_context 的绑定规则：
- 每个任务在创建时快照当前 page_context，后续执行全程使用该快照
- 页面切换不影响已发起任务的上下文
- 新任务使用切换后的 page_context

### 12. ReAct 机制：轻量级多步推理

**核心原则：不是所有请求都进 ReAct。由 LLM 第一轮输出的结构特征决定执行路径，不需要额外分类器。**

路径判定标准（Tool Dispatcher 根据 LLM 输出判定）：

| LLM 第一轮输出 | 判定 | 路径 |
|----------------|------|------|
| 单个 Tool Call + 参数完整 | 单步直达 | 执行 → 结果给 LLM → 生成回复 → 返回 |
| 多个 Tool Call（并行无依赖） | 单步并行 | 并行执行 → 结果合并给 LLM → 生成回复 |
| 多个 Tool Call（有依赖链） | 进入 ReAct | 按依赖顺序逐步执行 |
| 单个 Tool Call + 后续意图表达 | 进入 ReAct | 执行 → 观察 → 继续循环 |
| 无 Tool Call（纯文本/澄清） | 直接返回 | 不进入执行流程 |

ReAct 约束：
- 最大步数限制：单次对话最多 5 轮循环
- 写操作打断：ReAct 链中遇到写操作时暂停，展示确认，确认后继续
- 不引入外部 Agent 框架，Go 原生实现循环控制器

System Prompt 指令：
- 能一次 Tool Call 完成的，直接输出单个 Tool Call
- 需要多个独立数据的，输出多个并行 Tool Call
- 只有后续参数依赖前一步结果时，才输出单个 Tool Call 并说明后续计划

执行反馈策略（预估 + 骨架屏为主，步骤通知为辅）：

进入 ReAct 或多步执行时，Tool Dispatcher 返回执行计划摘要：
```json
{
  "type": "execution_plan",
  "steps": 3,
  "estimated_seconds": 8,
  "description": "需要查询资产、负债和预算数据后综合分析"
}
```

前端处理：
- 收到 execution_plan 后展示带进度预估的骨架屏
- 进度条按预估时间匀速推进（不依赖服务端推送）
- 每步 Tool 完成后推送 `{"type": "step_done", "step": 1, "total": 3}`（有则更好，没有不影响）
- 所有步骤完成后，最终回复走正常流式输出

可靠性保障：
- 最差情况（降级 + 弱网）：用户看到预估时间 + 匀速进度条，体验可接受
- 正常情况：进度条按实际步骤跳跃，体验更精确
- 核心体验不依赖不稳定的中间推送

性能预期：

| 路径 | LLM 调用次数 | 预期延迟 |
|------|-------------|----------|
| 单步直达 | 2 次 | 3~5s |
| 单步并行 | 2 次（Tool 并行） | 4~7s |
| ReAct 2 步 | 3 次 | 7~10s |
| ReAct 3 步 | 4 次 | 10~12s |

### 13. 记忆系统向量化策略

**核心原则：不是所有记忆都需要向量化。按检索方式决定存储策略。**

| 记忆层 | MySQL（结构化存储） | Milvus（向量化） | Redis | 检索方式 |
|--------|---------------------|------------------|-------|----------|
| L1 用户画像 | 结构化标签字段 | 不需要 | — | 按 user_id 精确查询 |
| L2 事实记忆 | 结构化字段（金额、分类、实体） | 文本描述做向量化 | — | 精确查询 + 语义检索双通道 |
| L3 情景记忆 | 元数据（时间、关联 op_log_id） | 场景描述做向量化 | — | 主要走语义检索 |
| L4 对话历史 | 归档（超出窗口的历史） | 不需要 | 最近 N 轮 | 按时间顺序取最近轮次 |

L2 双通道检索示例：
- 精确查询："用户月租多少" → MySQL `WHERE user_id=? AND fact_type='rent'`
- 语义检索："用户的固定支出有哪些" → Milvus 向量相似度匹配

向量化时机：
- L2 事实记忆：写入/更新时同步生成 Embedding 并写入 Milvus
- L3 情景记忆：写入时异步生成 Embedding（情景记忆写入频率较高，异步避免阻塞）

### 14. Embedding 模型抽象

**在 LLM 抽象层中增加 Embedding 接口，与 Chat 接口平级。**

```
LLMProvider interface {
    Chat(ctx, messages, tools) → stream
    Embedding(ctx, texts) → []vector
}
```

- 初期使用 LLM 提供商的 Embedding API（如 OpenAI text-embedding-3-small、Claude 等）
- 通过 interface 抽象，后续可切换为本地模型或其他提供商
- Embedding 维度统一为固定值（如 1536），切换模型时需要重建 Milvus 索引
- 批量 Embedding 支持：预计算场景下批量处理，减少 API 调用次数

### 15. Session 生命周期与清理策略

**Session 过期策略：**
- Session 记录最后活跃时间（last_active_at）
- 7 天无活动自动过期，释放 Redis 中的对话历史
- 用户重新登录时创建新 Session，但长期记忆（L1~L3）不受影响

**对话历史（L4）窗口管理：**
- Redis 中保留最近 50 轮对话（滑动窗口）
- 超出窗口的对话归档到 MySQL（可查询但不常驻内存）
- LLM 上下文注入策略：最近 10~20 轮完整对话 + 更早对话的摘要（由 LLM 生成）
- 摘要生成时机：每 20 轮对话触发一次摘要，摘要存入 Redis 替代原始对话

**未完成任务处理：**
- 用户断开连接时，进行中的只读任务继续执行，结果缓存等待用户重连后推送
- 进行中的写操作（待确认状态）：暂存确认请求，用户重连后提示"你有一个待确认的操作"
- 超过 5 分钟未确认的写操作自动取消，避免悬挂状态
- ReAct 链中断：已执行的只读步骤结果缓存，用户重连后从断点继续或重新开始

### 16. 预计算调度机制

**双触发机制：定时 + 事件驱动**

定时预计算：
- 每天凌晨全量刷新所有用户的核心指标（月度汇总、分类占比、预算执行率）
- 按 user_id 哈希分散执行时间（如 user_id % 60 = 分钟偏移），避免同时触发
- 预计算结果写入 Redis，设置 TTL = 25 小时（覆盖到下次刷新 + 1 小时容错）

事件驱动刷新：
- 写操作完成后，Op Logger 发布事件（如 `bill_created`、`budget_updated`）
- Analytics Engine 订阅事件，异步刷新受影响的缓存 key
- 刷新粒度：只刷新受影响的指标，不全量重算
  - 新增账单 → 刷新该分类的月度汇总、总支出、预算执行率
  - 修改预算 → 刷新该分类的预算执行率
- 事件处理设置 100ms 去抖（debounce），批量写操作合并为一次刷新

缓存未命中策略：
- Redis 缓存未命中时走实时计算，计算结果回填缓存
- 实时计算设置超时（3s），超时返回"数据计算中，请稍后"而非阻塞

### 17. Skill 冲突解决规则

**优先级：DB 层 > 文件层（同名时 DB 覆盖）**

加载顺序：
1. 启动时加载文件层所有 Skill（基础集）
2. 从 DB 加载所有 Skill，同名覆盖文件层版本
3. 运行时 DB 层变更通过轮询（如 10s 间隔）或事件通知热更新
4. 文件层变更通过 fsnotify 监听热更新

DB 层 Skill 状态管理：
- 每个 DB Skill 有 `status` 字段：`enabled` / `disabled`
- `enabled`：覆盖文件层同名 Skill
- `disabled`：自动回退到文件层版本（如果存在），否则该 Skill 不可用
- 支持一键禁用，用于 DB 层 Skill 出 bug 时快速回退

版本追溯：
- DB 层 Skill 记录 `overrides_file_version` 字段，标记被覆盖的文件层版本
- 文件层 Skill 在文件头部声明版本号（如 `version: 1.2.0`）
- 回退时可对比 DB 版本与文件层版本的差异

灰度发布（后续扩展）：
- DB 层 Skill 支持 `gray_ratio` 字段（0~100），按用户 ID 哈希决定是否命中新版本
- prototype 阶段不实现，但数据模型预留字段

### 18. 反幻觉数值校验优化

**原方案问题：从自然语言中提取数值并比对，实现复杂且不可靠。**

**优化方案：LLM 输出结构化数据引用，校验走 JSON 比对。**

LLM 输出格式约束：
```json
{
  "display": "本月外卖共消费 2,180 元，比上月（1,850 元）多了 330 元，环比增长 17.8%。",
  "data_ref": {
    "current_month_total": 2180,
    "last_month_total": 1850,
    "diff": 330,
    "growth_rate": 0.178
  },
  "tool_results_used": ["bill_statistics_result_001"]
}
```

校验流程：
1. Tool 执行后，结果以唯一 ID 存入当前会话的临时存储
2. LLM 生成回复时，`data_ref` 中引用的数值必须与 Tool 返回的原始数据一致
3. Tool Dispatcher 做 JSON 级别的数值比对（精确匹配 + 允许合理的四舍五入误差 ≤0.5%）
4. `growth_rate` 等派生值：校验计算公式是否正确（(2180-1850)/1850 ≈ 0.178）

校验结果处理：
- 全部一致 → 放行
- 原始数值不一致 → 用 Tool 原始数据替换 `display` 中的错误数值，修正后返回
- 派生值计算错误 → 用正确计算结果替换
- 校验耗时：纯 JSON 比对 + 简单算术校验，确实可控在 ≤100ms

System Prompt 中的格式约束指令：
> 你的每次回复必须包含 display 和 data_ref 两个字段。display 是给用户看的自然语言回复。data_ref 是你引用的所有数值的结构化列表，必须与工具返回的原始数据完全一致。不要在 display 中使用任何未在 data_ref 中列出的数值。

### 19. 对话消息 Markdown 渲染策略

**问题：** LLM 返回的 display 字段包含 markdown 格式（表格、列表、加粗等），ChatWindow.vue 使用 `{{ msg.content }}` 纯文本渲染，导致 markdown 表格显示为原始 pipe-separated 文本，体验差。

**方案：引入 marked.js + DOMPurify 做轻量 Markdown 渲染**

选型依据：
- marked.js：~40KB gzip，零依赖，GitHub 33k+ stars，专注 markdown→HTML 转换
- DOMPurify：~7KB gzip，防 XSS 必备，LLM 输出不可信必须 sanitize
- 总增量 < 50KB，对前端包体积影响可忽略

渲染链路：
```
LLM display (markdown) → marked.parse() → DOMPurify.sanitize() → v-html 渲染
```

安全措施：
- DOMPurify 白名单：只允许 `<table>`, `<thead>`, `<tbody>`, `<tr>`, `<th>`, `<td>`, `<p>`, `<strong>`, `<em>`, `<ul>`, `<ol>`, `<li>`, `<br>`, `<code>`, `<pre>`, `<h1>`~`<h6>`, `<blockquote>` 等安全标签
- 禁止 `<script>`, `<iframe>`, `<img>`, `<a>` 的 `javascript:` 协议
- `<a>` 标签强制 `target="_blank"` + `rel="noopener noreferrer"`

不选的方案：
- ❌ 修改 Tool 返回 HTML — 违反数据/展示分离原则，Tool 只返回结构化数据
- ❌ 前端自己解析 markdown 子集 — 不完整，后续遇到新格式还要改
- ❌ 禁止 LLM 输出 markdown — 不现实，LLM 天然倾向用 markdown 组织信息
- ❌ markdown-it — 功能更强但体积更大（~100KB），本场景不需要插件生态

样式要求：
- 表格：带边框、斑马纹、紧凑间距，适配聊天气泡宽度
- 列表：适当缩进，项目符号清晰
- 代码块：灰底、等宽字体
- 整体：继承聊天气泡的字体和颜色，不引入额外的 markdown 主题

影响范围：
- 仅修改 `web/src/components/ChatWindow.vue`
- assistant 消息使用 `v-html` + markdown 渲染
- user 消息保持纯文本（用户输入不需要 markdown）
- thinking 区块保持纯文本（推理过程不需要格式化）

### 20. 对话历史数据隔离策略（防 LLM 历史数据引用）

> **本决策是 v2.0 Engine 架构的核心防线之一，后续任何涉及对话历史注入的改动必须参考本文档。**

#### 一、问题根因链

v2.0 的核心原则是"所有数据必须来自 Tool 返回"，但对话历史注入形成了一条绕过 Tool 的数据通道：

```
Redis 完整对话历史 → 原样注入 LLM 消息列表 → LLM 看到历史中的金额/统计 → 直接引用回答
```

这条通道导致的已知问题：
| 场景 | 表现 | 根因 |
|------|------|------|
| 用户说"咖啡"，LLM 填了 9.9 元 | 从历史中复用金额 | 历史中有"咖啡 9.9 元" |
| 用户问"近期记账行为"，AI 说"今天" | 引用历史中的相对日期 | 历史中有"今天在大米先生消费" |
| 用户问"花了多少"，LLM 自己算 | 从历史中的账单数据求和 | 历史中有多笔账单金额 |

当前防线体系的覆盖缺口：
- System Prompt 第 4 条规则（"不要从对话历史引用金额"）→ **软约束，LLM 可能忽略**
- amountFoundInContext → **只在 create_bill 时校验，不覆盖查询场景**
- validateResponse → **只拦截"无 Tool 却声称操作完成"，不拦截"从历史引用数据回答查询"**
- persistConversation 日期替换 → **只解决相对日期问题，不解决金额引用**

**缺失的防线：对话历史注入时的数据脱敏。** 这是唯一能从源头解决问题的方案——LLM 看不到数据，就不可能引用。

#### 二、核心矛盾

对话历史中的数据有两种用途，必须区分对待：

| 用途 | 示例 | 需要具体数值？ |
|------|------|----------------|
| 上下文连贯（指代消解） | "把那笔改成 40" → 需要知道"那笔"是什么 | 需要标识（商户、分类），不需要金额 |
| 数据查询（替代 Tool） | "花了多少" → LLM 从历史中算 | 不需要（应该调 Tool） |

**核心洞察：对话历史应该保留"做了什么"（操作语义），但脱敏"具体数值"（数据细节）。**

但完全脱敏会破坏近期上下文连贯性——用户说"刚才那笔多少钱"，如果最近的回复也被脱敏了，LLM 就必须调 Tool 查询，增加一次调用延迟。

#### 三、方案设计：分层注入 + assistant 消息脱敏

**注入结构：**
```
System Prompt
  ↓
远期历史（第 N~4 轮）：assistant 消息脱敏，user 消息保留原文
  ↓
近期历史（最近 3 轮）：完整保留，user + assistant 原文
  ↓
当前 user 消息
```

**为什么是 3 轮而不是 1 轮：**
多轮补参场景通常是 2-3 轮对话（用户说"咖啡" → AI 追问金额 → 用户说"9.9" → AI 追问分类 → 用户说"饮品"）。保留 3 轮（6 条消息）确保补参链路完整。

**脱敏规则（仅针对远期 assistant 消息）：**

1. **金额脱敏**：用正则匹配 `¥xxx.xx`、`xxx元`、`xxx块` 等金额模式，替换为 `¥***`
2. **统计数据脱敏**：匹配"共xxx笔"、"总计xxx"、"环比xxx%"等模式，替换为 `[数据已省略，请通过工具查询]`
3. **操作语义保留**：保留操作类型词（"已记录"、"已创建"、"已删除"）和对象词（商户名、分类名）
4. **追问消息保留**：包含问号的 assistant 消息不脱敏（追问不含敏感数据，且是上下文连贯的关键）
5. **user 消息永不脱敏**：用户说了什么不能篡改

**脱敏示例：**
```
原文：已记录：今天午饭 ¥30.00，分类食饮（三餐）。食饮预算已花 ¥205.00，超出预算 ¥120.00。
脱敏：已记录：午饭，分类食饮（三餐）。食饮预算执行情况请通过工具查询。

原文：2026-04-28 至 2026-04-30 共 12 笔账单，最高分类 食饮 ¥156.80（占 45.2%）
脱敏：2026-04-28 至 2026-04-30 的账单统计 [数据已省略，请通过工具查询]

原文：请问是什么类型的收入？工资、奖金、兼职还是其他？
脱敏：（不脱敏，保留原文）
```

#### 四、实现要点

**位置：** `internal/engine/engine.go` 新增 `buildHistoryMessages` 方法

**关键设计：**
- **不修改 Redis 中的原始数据**，只在注入 LLM 时做实时脱敏
- Redis 存完整版（前端展示用），LLM 拿脱敏版（推理用）
- 脱敏逻辑在 Go 端用正则实现，不依赖 LLM，性能开销可忽略

**脱敏正则策略（而非从 display 文本提取语义）：**
```
金额模式：¥[\d,]+\.?\d*  |  \d+(\.\d+)?元  |  \d+(\.\d+)?块
统计模式：共\s*\d+\s*笔  |  总[计共]?\s*¥?[\d,]+  |  环比[\d.]+%  |  占[\d.]+%
```
用正则替换比从文本中提取语义更健壮——不需要理解 LLM 回复的格式，只需要把数值模式替换掉。

#### 五、场景验证矩阵

| 场景 | 对话历史状态 | LLM 行为 | 正确？ |
|------|-------------|----------|--------|
| "刚才那笔多少钱" | 最近 3 轮完整 | 直接回答 | ✅ |
| "咖啡"（编造金额） | 远期历史已脱敏 | 没有金额可引用，追问 | ✅ |
| "近期记账行为" | 远期历史保留操作语义 | 知道记过账但没有具体数据，调 Tool | ✅ |
| "这个月花了多少" | 历史中统计数据已脱敏 | 必须调 Tool | ✅ |
| "把那笔改成 40" | 最近 3 轮完整 | 正确识别指代 | ✅ |
| "再来一笔一样的" | 最近 3 轮完整 | 正确复制 | ✅ |
| 连续记 5 笔，问"第一笔多少" | 第一笔已在远期，金额脱敏 | 调 Tool 查询，体验略慢但数据准确 | ✅ |
| "和刚才一样" | 最近 3 轮完整 | 能理解"刚才" | ✅ |

#### 六、与现有防线的协同

本方案是**源头防线**，与现有防线形成纵深防御：

```
第 1 层（源头）：对话历史脱敏 → LLM 看不到远期数据 [本方案]
第 2 层（Prompt）：System Prompt 规则 → 软约束 LLM 不引用历史数据 [已有]
第 3 层（写入）：amountFoundInContext → 校验 create_bill 的金额来源 [已有]
第 4 层（输出）：validateResponse → 拦截无 Tool 的操作声明 [已有]
第 5 层（存储）：persistConversation 日期替换 → 消除相对日期歧义 [已有]
```

#### 七、不可变规则（后续改动必须遵守）

1. **Redis 存完整版，LLM 拿脱敏版** — 两条数据流永远分离
2. **user 消息永不脱敏** — 用户说了什么不能篡改
3. **近期 3 轮完整保留** — 多轮补参和指代消解的生命线
4. **脱敏用正则替换，不用语义提取** — 正则健壮且无 LLM 格式依赖
5. **追问消息（含问号）不脱敏** — 追问是上下文连贯的关键
6. **任何新增的 Tool 返回数据格式变化，必须同步检查脱敏正则是否覆盖**

### 21. PendingAction 确认机制
- Tool 返回 need_confirm 时，Engine 把 Tool 名称和参数存入 PendingStore（内存，5分钟过期）
- 用户说"确认"时，Engine 在 Chat 入口检测确认意图，从 PendingStore 取出操作直接执行 Tool，跳过 LLM
- 用户说"取消"时，清除 PendingAction，直接返回"好的，已取消"
- 效果：确认操作从 ~10s 降到 <1s

### 22. LLM 计算硬拦截
- 问题：LLM 拿到 Tool 返回的数值后自己做加减法，算出错误结果
- 方案：executeWorkflow 中 LLM 生成最终回复时，提取回复中所有 ¥ 金额，与 Tool message 中的金额比对
- 如果出现 Tool 数据中不存在的金额（说明 LLM 自己算了），用最后一个写操作 Tool 的 message 替换 LLM 回复
- 实现：containsUnverifiedAmount + buildToolMessageReply

### 23. 总预算约束机制
- 总预算是硬约束上限，已花 = 当月所有支出之和
- 分类预算之和 ≤ 总预算
- 创建/调整分类预算时自动校验，超出时返回 need_confirm 提示用户先调整总预算
- 调整总预算时返回"当前分类预算合计 + 总预算余量"
- 总预算判定：name="总预算" 或 categories 为空

### 24. 消费分析固定模板
- 问题：LLM 拿到分类汇总数据后自由发挥写"偏好分析"，自己做除法算平均值，编造"低于95%用户"等数据
- 方案：Tool 返回的 message 本身就是完整的最终文案（固定模板），LLM 只需转述
- GenerateSpendingReport 固定 3 个维度：消费概览（总额/笔数/分类数）、分类明细、消费特征（集中度/最频繁/大额支出）
- 所有数值由 Engine 计算，不给 LLM 做计算的空间

### 25. LLM 超时降级策略
- LLM 调用设 30s 超时（withLLMTimeout）
- 超时返回友好提示"AI 响应超时了，请稍后再试"
- ReAct 中间步骤 LLM 失败时，用已有 Tool 结果兜底
- Milvus 不可用时降级到 MySQL keyword search
- Redis 对话历史获取失败时跳过历史注入继续对话
